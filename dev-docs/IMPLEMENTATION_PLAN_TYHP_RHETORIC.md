# Implementation Plan: `tyhp/rhetoric` — typed, lambda-driven data access for Laravel

> **Status:** Proposed. Nothing in this document is implemented yet.
> Phase 0 outcomes are recorded in [Phase 0 outcomes](#phase-0-outcomes). Later phases are not started.
> **Package:** `tyhp/rhetoric` (namespace `Tyhp\Rhetoric`, artisan prefix `rhetoric:`). The name is a companion to
> Laravel's Eloquent: rhetoric is the craft behind eloquent speech.
> **Location:** `packages/tyhp/rhetoric/` (compiled runtime package built from `tyhp_src/`, like `tyhp/lambda`)
> **Depends on:** `tyhp/core`, `tyhp/lambda`, `illuminate/database` (+ `illuminate/support`, `illuminate/console`
> for the Laravel integration), and the matching `tyhpdef/illuminate-*` companions already in `packages/tyhpdef/`.
> **Compiler prerequisites:** some query features need expression-tree work in the sibling `tyhp` repo. They are
> listed in [Tyhp prerequisites](#tyhp-prerequisites-fix-tyhp-first) and scheduled so v1 does not block on them.
> **Reference design:** Microsoft's Entity Framework Core. This plan reviews its feature set and maps each feature
> onto Rhetoric and Laravel. Rhetoric uses its own names and does not reuse EF's type names.

---

## Summary

Entity Framework Core gives C# developers four things Laravel's Eloquent does not:

1. **Typed, compiler-checked queries** written as lambdas (`Where(p => p.Rating > 3)`), translated to SQL.
2. **Plain model classes** with real typed properties, mapped by conventions, attributes, or a fluent API.
3. **A unit of work** with an identity map, change tracking, and a single save call that writes a whole object graph
   in dependency order inside one transaction.
4. **Model-driven tooling**: code-first migrations generated by diffing the model against a snapshot, and db-first
   reverse engineering that generates models and a context from an existing schema.

Tyhp's parsable lambdas (`Expression<callable(T): R>` / `PropertyPath<callable(T): R>`, package `tyhp/lambda`)
give PHP the missing ingredient: the query lambda arrives at runtime as an expression tree that a library can
translate. Rhetoric builds this layer on top of that **without replacing Laravel's database stack**:

- SQL generation goes through Laravel's `Illuminate\Database\Query\Builder` and its per-driver grammars, so MySQL,
  MariaDB, PostgreSQL, SQLite, and SQL Server work the way they already do in Laravel.
- Connections, `config/database.php`, read/write splitting, `DB::listen`, Telescope, Debugbar, and
  `DB::transaction()` all keep working, because every query runs on a Laravel `Connection`.
- Code-first migrations are generated as **ordinary Laravel migration classes** using `Schema` / `Blueprint`.
  `php artisan migrate`, `migrate:rollback`, `migrate:status`, `migrate --pretend`, and `schema:dump` are unchanged.
- Default naming conventions match Eloquent's (snake_case plural tables, snake_case columns, `<relation>_id`
  foreign keys, `created_at` / `updated_at` / `deleted_at`, alphabetical pivot tables), so Rhetoric models and
  Eloquent models can share tables and transactions in the same app.
- Method names follow Laravel where Laravel already has a word for the concept (`with`, `orderByDesc`, `sole`,
  `firstOrFail`, `paginate`, global scopes, casts, observers, `withTrashed`).

## Goals

- Typed query API over model classes: filtering, projection, ordering, paging, aggregates, eager loading, joins,
  grouping, set operations, bulk update/delete, raw SQL escape hatches.
- `Context` / `Table<T>` unit of work with identity resolution, snapshot change tracking, and `save()`.
- Mapping by convention, by attributes, and by a fluent `Mapper` that uses `PropertyPath` lambdas instead of strings.
- **Code-first:** `artisan` command that diffs the mapping against a stored snapshot and writes a Laravel migration.
- **DB-first:** `artisan` command that reads the live schema through Laravel's `Schema` inspection API and writes
  Tyhp model classes, a context, and mappings.
- Adoption path for existing Laravel apps: baseline an existing database, then continue code-first.
- **Opt-in auto-migrator:** apply pending migrations when the app loads, with a near-free check on every request,
  one migrating process at a time, deferred migrations for large changes, and per-connection migration sets for
  multi-tenant apps.
- Everything is Tyhp source compiled to PHP 8.3–8.5, published like the other `tyhp/*` runtime packages.

## Non-goals

- Replacing Eloquent. Eloquent keeps working. The typed-query bridge over Eloquent models is required (Phase 12).
- Shipping our own SQL dialects or schema grammars. If Laravel's grammar can't express something, we use the
  builder's `*Raw` methods with grammar-wrapped identifiers rather than forking a grammar.
- EF features with no Laravel foundation and low demand in PHP: spatial types, temporal tables, NoSQL providers,
  HiLo/sequence key generation, context pooling (Octane scoped bindings cover the need).

## Why this is needed (current Tyhp + Laravel experience)

`tyhp-examples/chirper` is a Laravel app written in Tyhp. With Eloquent, model attributes are untyped and relations
are referenced by string, so Tyhp's type system has nothing to check:

```tyhp
// ChirpController::currentUserOwns — attribute is mixed, so the code needs runtime guards
$ownerId = $chirp->user_id;
if (\is_int($ownerId)) {
    return $ownerId === $actorId;
}

// ChirpController::index — relation name is a string
$chirpsQuery = Chirp::with('user')->latest();
```

The Rhetoric equivalent is fully typed and checked by the compiler:

```tyhp
array<Chirp> $chirps = $db->chirps
    ->with(fn ($c) => $c->user)
    ->orderByDesc(fn ($c) => $c->createdAt)
    ->take(50)
    ->all();

bool $owns = $chirp->userId === $actorId;
```

## Developer experience sketch (target API)

These samples define the intended surface. Exact names are settled in Phases 2–3. Each `fn` passed to a query or
mapping method is an inline lambda captured as an `Expression` / `PropertyPath` tree.

### Models (plain Tyhp classes)

```tyhp
<?tyhp
namespace App\Data\Models;

use Tyhp\Rhetoric\Attributes\MaxLength;

class Blog {
    public int $id = 0;
    #[MaxLength(200)]
    public string $name = '';
    public ?string $url = null;
    public array<Post> $posts = [];
}

class Post {
    public int $id = 0;
    public int $blogId = 0;
    public ?Blog $blog = null;
    public string $title = '';
    public string $slug = '';
    public int $rating = 0;
    public ?\DateTimeImmutable $publishedAt = null;
    public ?\DateTimeImmutable $deletedAt = null;
}
```

Conventions alone map these to `blogs(id, name, url)` and `posts(id, blog_id, title, slug, rating, published_at,
deleted_at)` with a `posts.blog_id → blogs.id` foreign key, and pair `Blog::$posts` (an `array<Post>`) with
`Post::$blog` as one relationship. Attributes and the fluent mapper override conventions.

### Context

```tyhp
<?tyhp
namespace App\Data;

use App\Data\Models\Blog;
use App\Data\Models\Post;
use Tyhp\Rhetoric\Context;
use Tyhp\Rhetoric\Mapping\Mapper;
use Tyhp\Rhetoric\OnDelete;
use Tyhp\Rhetoric\Table;

final class BlogContext extends Context {
    protected ?string $connection = null;   // Laravel connection name; null = default connection

    public Table<Blog> $blogs { get => $this->table<Blog>(); }
    public Table<Post> $posts { get => $this->table<Post>(); }

    protected function map(Mapper $map): void {
        $map->model<Post>()
            ->hasIndex(fn ($p) => $p->slug)
            ->unique();

        $map->model<Post>()
            ->belongsTo(fn ($p) => $p->blog)
            ->inverseOf(fn ($b) => $b->posts)
            ->foreignKey(fn ($p) => $p->blogId)
            ->onDelete(OnDelete::Cascade);

        $map->model<Post>()
            ->addGlobalScope(fn ($p) => $p->deletedAt === null);
    }
}
```

### Queries

```tyhp
int $minRating = 3;

array<Post> $posts = $db->posts
    ->where(fn ($p) => $p->rating >= $minRating && $p->title->startsWith('Tyhp'))
    ->with(fn ($p) => $p->blog)
    ->orderByDesc(fn ($p) => $p->publishedAt)
    ->thenBy(fn ($p) => $p->id)
    ->skip(20)
    ->take(10)
    ->all();                                   // array<Post>; ->get() returns a Laravel Collection<int, Post>

?Post $post = $db->posts->first(fn ($p) => $p->slug === $slug);
Post $only = $db->posts->sole(fn ($p) => $p->slug === $slug);   // throws on zero or several rows

array<PostSummary> $summaries = $db->posts
    ->where(fn ($p) => $p->blog->name === 'News')        // navigation → implicit join
    ->select(fn ($p) => new PostSummary($p->id, $p->title, $p->blog->name))
    ->all();

int $count = $db->posts->count(fn ($p) => $p->rating > 4);
bool $found = $db->posts->exists(fn ($p) => $ids->contains($p->id));   // captured array → IN (...)
```

Captured variables (`$minRating`, `$slug`, `$ids`) arrive in the tree as `ConstantExpression` values and are always
sent as bound parameters, never interpolated.

### Saving

```tyhp
$blog = new Blog();
$blog->name = 'Tyhp news';
$db->blogs->add($blog);

?Post $post = $db->posts->find(42);
if ($post !== null) {
    $post->rating = 5;            // detected by snapshot comparison
}

int $written = $db->save();       // one transaction: INSERT blogs, UPDATE posts
```

### Bulk operations (no tracking, single statement)

```tyhp
int $deleted = $db->posts
    ->where(fn ($p) => $p->deletedAt !== null)
    ->delete();

int $bumped = $db->posts
    ->where(fn ($p) => $p->blogId === $blogId)
    ->increment(fn ($p) => $p->rating);

int $updated = $db->posts
    ->where(fn ($p) => $p->blogId === $blogId)
    ->update(fn (Assignments<Post> $set) => $set
        ->assign(fn ($p) => $p->rating, fn ($p) => $p->rating + 1));
```

### Tooling

```bash
# code-first
php artisan rhetoric:migration AddPostRating --context="App\Data\BlogContext"
php artisan migrate                      # Laravel's migrator, unchanged

# db-first
php artisan rhetoric:scaffold --connection=mysql --context=LegacyContext --namespace="App\Data\Legacy"

# CI guard: fail when the mapping has changes with no migration
php artisan rhetoric:pending

# opt-in auto-migrator (RHETORIC_AUTO_MIGRATE=true): large or destructive changes run later
php artisan rhetoric:migration DropPostLegacySlug --defer
php artisan rhetoric:migrate-deferred
```

### Query pipeline

1. **Compose.** `Table<T>` is the root `Query<T>`. Every operator returns a new immutable `Query` that appends an
   operator node holding the user's `Expression` / `PropertyPath`. Nothing runs until a terminal operator
   (`all`, `get`, `first`, `count`, `delete`, ...).
2. **Normalize.** Operators fold into a `QueryPlan`: root model, implicit joins from navigation access, predicate
   list, ordering, projection, eager loads, `skip`/`take`, tracking mode, tags, global scopes.
3. **Translate.** Visitors extending `Tyhp\Expression\ExpressionVisitor` walk each tree against the mapping:
   - `ParameterExpression` → the root alias (or join alias for multi-parameter lambdas).
   - `PropertyAccessExpression` on a parameter → qualified column. On a reference navigation → join + column.
   - `ConstantExpression` → bound parameter. A captured `Context` instance is rebound to the executing context.
   - `BinaryExpression` → comparison / boolean groups / arithmetic, with null-semantics rewriting.
   - `MethodCallExpression` / `StaticMethodCallExpression` → `MethodTranslatorRegistry`.
   - `TernaryExpression` / `CoalesceExpression` / `CastExpression` → `CASE` / `COALESCE` / `CAST`.
   - `InstanceofExpression` → discriminator filter (single-table inheritance).
   - `NewExpression` in the final projection → selected columns + client-side construction.
   - Anything else → `QueryTranslationException` (except inside the top-level projection, which may fall back to
     client evaluation with `Expression::compile()` over hydrated values).
4. **Build.** Translation targets `Illuminate\Database\Query\Builder` (`where`, `whereIn`, `whereNull`, `whereExists`,
   `join`, `orderBy`, `selectRaw`, ...). Identifiers in raw fragments are wrapped with the connection's grammar.
5. **Cache.** The translated plan is cached by tree shape (operators + node structure, constants excluded), so a
   repeated query only rebinds parameters.
6. **Execute + hydrate.** Rows become models through constructor binding or `newInstanceWithoutConstructor()` plus
   property writes, with casts applied. Tracked queries resolve through the identity map, record snapshots, and run
   navigation fix-up. Eager loads run as follow-up queries (`whereIn` on loaded keys).

### Save pipeline

1. `detectChanges()` compares tracked models with their snapshots and walks navigations for newly reachable models
   (graph add).
2. Build commands: insert / update (changed columns only) / delete, plus pivot rows for many-to-many.
3. Topologically sort by foreign-key dependency (inserts parent → child, deletes child → parent). Cycles that need a
   nullable FK are split into insert-then-update.
4. Dispatch observer `saving` / `creating` / `updating` / `deleting` callbacks.
5. Execute in `Connection::transaction()` unless the connection already has an open transaction
   (`transactionLevel() > 0`), in which case the save joins it.
6. Propagate generated keys (`insertGetId`) into dependents' FK properties before their inserts run.
7. On success, mark models `Clean`, refresh snapshots, and dispatch `saved` / `created` / `updated` / `deleted`. On
   failure, leave tracking state as it was and rethrow (concurrency failures become `ConcurrencyException`).

### Mapping metadata

The `ContextMap` is immutable after build and cached per context class. It records model maps, table names, columns
(type, nullability, length, precision, default, generated), keys, indexes, foreign keys, relations (with inverse),
delete behavior, discriminators, casts, observers, and global scopes. The same map drives queries, saves, migrations
(serialized as the snapshot), and `rhetoric:show`.

Runtime type information comes from:

- PHP reflection for property names, native types, nullability, attributes, and constructor parameters.
- `typeof(T)` inside `Table<T>` / `Mapper::model<T>()` (runtime generic tracking in `tyhp/core`).
- `Type::fromProperty()` for types PHP erases: `array<Post>` reads as an array of `App\Post`, `?Table<Blog>` keeps
  its type argument, and structs and aliases resolve through the `tyhp/core` type registry. Metadata reads it
  instead of native reflection for every mapped property.

## Code-first workflow

1. The developer edits models or `map()`.
2. `php artisan rhetoric:migration AddPostRating` builds the current mapping, loads
   `database/rhetoric/BlogContext.snapshot.json`, and diffs them into operations.
3. The operations are written as a Laravel migration in `database/migrations/<timestamp>_add_post_rating.php`:

   ```php
   <?php

   use Illuminate\Database\Migrations\Migration;
   use Illuminate\Database\Schema\Blueprint;
   use Illuminate\Support\Facades\Schema;

   return new class extends Migration
   {
       public function up(): void
       {
           Schema::table('posts', function (Blueprint $table) {
               $table->integer('rating')->default(0);
           });
       }

       public function down(): void
       {
           Schema::table('posts', function (Blueprint $table) {
               $table->dropColumn('rating');
           });
       }
   };
   ```

4. The snapshot is rewritten. The migration header records the snapshot hash it was generated from, so
   `rhetoric:pending` can detect migrations generated on diverged branches.
5. `php artisan migrate` applies it with Laravel's migrator.

Differ rules:

- Renames are not guessed. A removed + added column of the same type prints a data-loss warning and suggests
  `--rename=old:new`, which emits `renameColumn`.
- Operations that lose data (drop column/table, narrowing type changes) are flagged in the console and with a
  comment in the generated migration.
- `down()` is generated from the inverse operations. Irreversible operations generate a `down()` that throws.
- Foreign keys are created after both tables exist. Drops run in reverse dependency order.

Type mapping (code-first direction; db-first is the inverse):

| Tyhp property type | Blueprint column | Notes |
| --- | --- | --- |
| `int` key by convention | `id()` (`bigIncrements`) | Matches Laravel's default `id`. |
| `int` | `integer` / `bigInteger` | `#[Column(type: 'bigInteger')]`, or a FK to a `bigIncrements` key → `foreignId`. |
| `string` | `string(255)` | `#[MaxLength(n)]` → `string(n)`; `#[Text]` → `text`. |
| `bool` | `boolean` | |
| `float` | `double` | `#[Precision]` → `float(p)`. |
| `decimal` (`tyhp/decimal`) | `decimal(p, s)` | Default precision configurable. |
| `\DateTimeImmutable` / Carbon | `dateTime` / `timestamp` | `#[Timestamps]` → `timestamps()`. |
| backed `enum` | `string` / `integer` (or `enum([...])` when configured) | |
| UUID / ULID value objects | `uuid` / `ulid` | |
| struct / `array<scalar>` with `asJson()` | `json` | |
| `?T` | `->nullable()` | |

## DB-first workflow

`php artisan rhetoric:scaffold` options: `--connection`, `--schema`, `--tables=a,b`, `--exclude=...`,
`--context=Name`, `--namespace=`, `--output=`, `--attributes` (attributes on models) or `--fluent` (mapping classes),
`--no-pluralize`, `--force`, `--baseline`.

1. `SchemaReader` reads `Schema::getTables()`, `getColumns()`, `getIndexes()`, `getForeignKeys()`, and
   `getViews()` for the chosen connection. These are driver-independent in Laravel, so every Laravel driver works.
2. `ReverseMapper` builds model maps: class names singularized and PascalCased, columns camelCased, Tyhp types from
   the reverse type map, keys and indexes from index metadata, `belongsTo` + `hasMany` relations from foreign keys,
   and `belongsToMany` for pure pivot tables (exactly two FKs forming the key, no other columns).
3. Mapping that conventions would not infer is written as attributes or fluent mapping classes.
4. Output is Tyhp source (`.tyhp`) for models, the context, and mapping classes.
5. With `--baseline`, the command also writes the context snapshot so the next `rhetoric:migration` only contains
   changes made after scaffolding. This is the adoption path for an existing Laravel app that already has
   migrations: its existing migrations stay as they are, and only new changes come from the mapping.

Re-scaffolding without losing hand edits (PHP has no partial classes): generated members go into a trait in a
`Generated/` folder (`trait PostColumns { ... }`), and the model class that `use`s it is written once and never
overwritten. See [Decision D6](#decisions).

## Auto-migrator

The auto-migrator is an opt-in service that applies pending migrations when the application loads, so a deploy
does not need a separate `php artisan migrate` step. It is the Rhetoric counterpart of calling EF Core's
`Database.Migrate()` at startup. EF Core 9 added a database-wide lock to `Migrate()` because several app instances
often start at once. This design has the same lock for the same reason. The auto-migrator is off by default.
Running `php artisan migrate` as a deploy step keeps working and needs no configuration.

The choices this section relies on are locked as D12–D19 in [Decisions](#decisions).

### Scope

- The auto-migrator lives entirely in `tyhp/rhetoric`, under `Tyhp\Rhetoric\Migrations\Auto`. Laravel wiring is in
  `Tyhp\Rhetoric\Laravel`. Eloquent and Laravel are not changed.
- It drives Laravel's `Illuminate\Database\Migrations\Migrator` over the configured migration paths. Every pending
  migration in those paths is applied, whether Rhetoric generated it, a developer wrote it by hand, or a package
  published it. Applied migrations are recorded in Laravel's migrations table through `DatabaseMigrationRepository`,
  so `migrate:status`, `migrate:rollback`, and `php artisan migrate` see the same state.
- `php artisan migrate` is unchanged. It applies every pending migration, including deferred ones.

### Opting in

The service is enabled through `config/rhetoric.php` (`auto_migrate.enabled`, or env `RHETORIC_AUTO_MIGRATE`) or
through `AutoMigrator::enable()`. When it is not enabled, the service provider registers no hooks, so it costs
nothing.

```php
<?php

return [
    // ... contexts, naming, snapshot path ...

    'auto_migrate' => [
        'enabled' => (bool) \env('RHETORIC_AUTO_MIGRATE', false),
        'environments' => null,              // null = every environment except "testing"

        // Connections checked when the app loads: connection name => migration set.
        'connections' => [
            'mysql' => 'app',
        ],

        // A migration set is a group of migration paths with its own migrations table.
        'sets' => [
            'app' => [
                'paths' => [\database_path('migrations')],
                'table' => 'migrations',
                'context' => \App\Data\AppContext::class,
            ],
            'tenant' => [
                'paths' => [\database_path('migrations/tenant')],
                'table' => 'migrations',
                'context' => \App\Data\TenantContext::class,
            ],
        ],

        'trigger' => 'boot',                 // HTTP: 'boot' (app booting hook) or 'middleware'
        'except_paths' => ['up'],            // HTTP paths that never wait, such as health checks
        'console' => [],                     // console commands that also check, for example ['schedule:run']
        'queue' => true,                     // check when a queue worker starts
        'octane' => true,                    // check when an Octane worker starts

        'lock' => [
            'driver' => 'database',          // 'database' (advisory lock) or 'cache'
            'store' => null,                 // cache store for the 'cache' driver
            'ttl' => 3600,                   // cache-lock expiry; longer than the slowest migration
        ],
        'wait' => ['http' => 10, 'console' => 300, 'queue' => 300],   // seconds a waiting process blocks
        'on_timeout' => 'throw',             // 'throw' (503 + Retry-After) or 'continue'
        'on_failure' => 'throw',             // 'throw' or 'continue' while a failed run is backing off
        'retry_after' => 15,                 // Retry-After seconds on 503 responses
        'failure_backoff' => [30, 600],      // first and maximum delay between attempts, in seconds

        'marker' => [
            'store' => 'file',               // 'file', 'apcu', or 'cache'
            'path' => \storage_path('framework/rhetoric'),
            'cache_store' => null,
        ],

        'deferred' => [
            'dispatch' => false,             // queue RunDeferredMigrations when a run leaves deferred work
            'queue' => null,
        ],
    ],
];
```

The same switch in code:

```tyhp
<?tyhp
namespace App\Providers;

use Illuminate\Support\ServiceProvider;
use Tyhp\Rhetoric\Migrations\Auto\AutoMigrator;

final class AppServiceProvider extends ServiceProvider {
    public function register(): void {
        AutoMigrator::enable(
            connections: ['mysql' => 'app'],
            environments: ['production', 'staging'],
        );
    }
}
```

Call `enable()` from `register()` so that the check runs in the app's booting hook, before any provider's
`boot()`. If you call it from `boot()`, the check runs at that point. Arguments override the matching config keys.
Sets, locks, and waits still come from config.

Where the check runs:

| Process | Trigger | Notes |
| --- | --- | --- |
| HTTP (PHP-FPM, `artisan serve`) | `Application::booting()` callback registered by `RhetoricServiceProvider::register()` (`trigger: 'boot'`) | Runs before any provider boots, so provider code that queries the database sees the new schema. Requests to `except_paths` skip the check. With `trigger: 'middleware'`, a global middleware added with `prependMiddleware()` runs the check instead, after boot. |
| Octane | `Laravel\Octane\Events\WorkerStarting` | Once per worker. Requests in that worker skip the check through the per-process memo. Tenant switches call `ensure()`. |
| Queue workers | `Illuminate\Queue\Events\WorkerStarting` | Once per worker start. `queue:restart` after a deploy starts new workers, which check again. |
| Console | skipped | Commands listed in `console` check at boot. `migrate`, `migrate:*`, `db:*`, `schema:*`, `rhetoric:*`, `optimize*`, `config:*`, and `package:discover` never check. |
| Tests | skipped | The `testing` environment is skipped unless `environments` lists it. Use `RefreshDatabase`. |

### Hot path

The check runs on every request, so it must be close to free. It compares two strings, an expected state and an
applied-state marker. It opens no database connection, scans no directories, and does no network I/O.

- **Expected state.** `rhetoric:cache` writes `bootstrap/cache/rhetoric-migrations.php`. For each set, the file
  holds a hash of the set config (paths, table) and the ordered migration names with their deferred flags. The
  package registers the command with `ServiceProvider::optimizes()`, so `php artisan optimize` builds the file and
  `optimize:clear` removes it. The file is plain PHP returning an array, so opcache serves it from shared memory.
  Like `config:cache`, a cached manifest is trusted as-is. Deploys rebuild it with `php artisan optimize`.
- **No manifest (local development).** The expected state is the hash of the set config plus `filemtime()` of each
  migration directory. Adding, removing, or renaming a migration file changes it. Editing an applied migration does
  not, which matches Laravel: an applied migration is never re-run. `rhetoric:migration` deletes a stale manifest.
- **Applied-state marker.** The marker is the expected-state hash that was last confirmed for one database, or a
  failure record. It is keyed by a hash of set name, driver, host, port, database, schema / search path, table
  prefix, and migrations table. The key comes from the connection's config array, so no connection is opened. The
  default store is a PHP file under `storage/framework/rhetoric/`, written to a temp file, renamed into place, and
  then `opcache_invalidate()`d. APCu and a shared cache store are optional alternatives; neither is required
  (D13).
- **No marker** (new server, cleared storage, APCu restart): the slow path checks the database once. If there is
  nothing to apply, it writes the marker.

```tyhp
// AutoMigrator::check(): runs once per configured connection on each request.
string $key = $this->markerKey($connection, $set);    // from config; no database connection
string $expected = $this->manifest->hash($set);       // opcache'd manifest, or directory mtimes
if (($this->verified[$key] ?? null) === $expected) {
    return;                                           // memo: Octane, queue workers, tenant switches
}
if ($this->markers->read($key) === $expected) {       // opcache'd marker file
    $this->verified[$key] = $expected;
    return;
}
$this->slowPath($connection, $set, $key, $expected);
```

Target cost: median ≤ 20 µs and p99 < 100 µs per request on PHP-FPM with opcache.

### Slow path

1. Read the marker record. If it is a failure record inside its backoff window, apply `on_failure` without touching
   the database (see [Waiting, timeouts, and failures](#waiting-timeouts-and-failures)).
2. Build a `Migrator` for the set: a `DatabaseMigrationRepository` on the set's `table` and `setConnection()` for the
   connection. Pending = `getMigrationFiles($paths)` minus `getRepository()->getRan()`. Deferred flags come from the
   manifest. Without a manifest, only the pending files are resolved to read them.
3. Build the run list. It holds the pending migrations in order, stopping at the first pending deferred migration
   that is not independent and skipping independent deferred ones (see
   [Deferred migrations](#deferred-migrations)). If the run list is empty, write the marker and return.
4. Acquire the migration lock for this set and database, waiting up to `wait.http` / `wait.console` / `wait.queue`.
5. Check again after acquiring the lock. If another process already applied the migrations, release the lock,
   write the marker, and return. This is how waiting processes continue once the migrating process finishes.
6. On an empty database, create the migrations table (`createRepository()`) and load the connection's schema dump
   first if there is one, the same way `php artisan migrate` does.
7. Call `runPending($runList)`. Laravel's migrator runs each `up()`, records it, dispatches its migration events, and
   wraps the migration in a transaction where the driver and the migration's `$withinTransaction` allow it.
8. Write the marker and release the lock. When deferred work remains and `deferred.dispatch` is on, dispatch
   `RunDeferredMigrations`. Then return a `MigrationResult`.

If any step throws, the auto-migrator writes a failure record (error, attempt count, next retry time), releases the
lock, logs the error, dispatches `AutoMigrationFailed`, and applies `on_failure`.

### Locking

Exactly one process migrates a given set on a given database at a time. Everyone else blocks on the same lock and
then takes the double-checked path in step 5.

| Driver | Acquire / release | Timeout | Released on crash |
| --- | --- | --- | --- |
| MySQL / MariaDB | `GET_LOCK(name, seconds)` / `RELEASE_LOCK(name)` | built-in argument | connection close |
| PostgreSQL | `pg_advisory_lock(key)` / `pg_advisory_unlock(key)`, 64-bit key from the name hash | `pg_try_advisory_lock` polling or `lock_timeout` (Phase 0) | session end |
| SQL Server | `sp_getapplock` with `@LockOwner = 'Session'` / `sp_releaseapplock` | `@LockTimeout` | session end |
| SQLite | `flock(LOCK_EX)` on a `<database file>.rhetoric-lock` file | `LOCK_NB` polling | process exit; `:memory:` databases skip locking |
| Cache (`lock.driver = 'cache'`) | `Cache::store($store)->lock($name, $ttl)`, `release()` | `block($seconds)` throws `LockTimeoutException` | `ttl` expiry |

- The lock name is `rhetoric-migrate:` plus the marker-key hash. That keeps it within MySQL's 64-character limit,
  and tenant databases lock independently.
- Advisory locks are taken on the connection that runs the migrations. They do not depend on DDL transaction
  behavior (MySQL DDL commits implicitly, and named locks are not transactional). Losing that connection releases
  the lock. Laravel reconnects after a lost connection when no transaction is open, and the new session does not
  hold the lock, so the auto-migrator re-checks lock ownership before each migration.
- The cache driver needs a store whose atomic locks are shared across servers (Redis, Memcached, DynamoDB, the
  database store). File and array stores lock within one machine only. Use the cache driver when advisory locks are
  not available, for example behind PgBouncer in transaction-pooling mode.

### Waiting, timeouts, and failures

- **Waiting.** A process that finds pending migrations blocks on the lock. When the migrating process finishes,
  the waiter re-checks, finds nothing pending, writes its marker, and continues.
- **Timeout.** With `on_timeout: 'throw'`, the waiter throws `MigrationsInProgressException`, which extends Symfony's
  `ServiceUnavailableHttpException`. Laravel renders it as a 503 with `Retry-After: retry_after`. In console and
  queue processes, the exception ends the command or the worker start, and the process supervisor restarts it. With
  `'continue'`, the request runs against the current schema and the timeout is logged.
- **Failure.** A failed run writes a failure record. Retries back off exponentially, starting at
  `failure_backoff[0]` and capped at `failure_backoff[1]`. Inside the window, servers do not retry. With
  `on_failure: 'throw'`, requests get `MigrationFailedException` (503). With `'continue'`, they run against the
  current schema. After fixing the cause, `rhetoric:auto-migrate --reset` clears the record.

### Deferred migrations

A deferred migration is pending by design. The auto-migrator never runs it during app load. Use deferred migrations
for long-running changes (index builds and table rewrites on large tables, backfills) and for the contract step of
an expand/contract change.

`rhetoric:migration DropPostLegacySlug --defer` writes two properties into the migration. Hand-written migrations
can add them too:

```php
return new class extends Migration
{
    public bool $deferred = true;
    public bool $independent = false;   // true: later migrations may run before this one

    public function up(): void
    {
        Schema::table('posts', function (Blueprint $table) {
            $table->dropColumn('legacy_slug');
        });
    }

    public function down(): void
    {
        Schema::table('posts', function (Blueprint $table) {
            $table->string('legacy_slug')->nullable();
        });
    }
};
```

Laravel's migrator ignores these properties, so `php artisan migrate` runs deferred migrations like any other.

Ordering rules:

- The auto-migrator applies pending migrations in order and stops at the first pending deferred migration. It does
  not stop at an independent deferred migration. That one is skipped, and later migrations still run.
- If the only pending migrations are deferred, the database counts as up to date. The marker is written and the
  hot path stays hot.
- If a non-independent deferred migration holds back later migrations, the status is `BlockedByDeferred`. It is
  logged once per manifest, and requests continue. The next deferred run applies the deferred migration and then the
  migrations behind it.
- `rhetoric:migration` suggests `--defer` when the diff contains data-loss operations (drop column or table,
  narrowing type changes).

Deferred migrations run through `php artisan rhetoric:migrate-deferred [--connection=] [--set=] [--only=]`, through
the scheduler (`Schedule::command('rhetoric:migrate-deferred')`), or through the `RunDeferredMigrations` job. All
three take the same lock as the auto-migrator, so they never overlap it.

### Expand/contract

During a rolling deploy, old and new code run against the same database. Changes that both versions can live with
can be applied automatically. Changes that break the old code wait until no old code is running:

1. **Expand** (normal migration, applied on load): add the new column or table as nullable or with a default. Large
   backfills go in a deferred migration.
2. **Switch** (code): release code that works with both shapes, for example code that writes both columns and reads
   the new one.
3. **Contract** (deferred migration): drop or rename the old column once every server runs the new code. Run it with
   `rhetoric:migrate-deferred`.

### Multi-tenant

- **Sets.** Each set in `auto_migrate.sets` has its own paths and migrations table, and names the context whose
  generated migrations go to the set's first path. Snapshots stay per context
  (`database/rhetoric/<Context>.snapshot.json`), so central and tenant schemas evolve separately.
- **On load vs on switch.** `connections` lists the connections checked on load. Tenant connections are usually not
  listed. After switching tenants, call
  `AutoMigrator::ensure(string $connection, ?string $set = null): MigrationResult`. It runs the same hot path and
  slow path. `$set` defaults to the `connections` entry, then to the only configured set.
- **One connection name, many databases.** The marker key includes driver, host, port, and database, so a
  `tenant` connection re-pointed at each tenant's database gets one marker per database. `ensure()` reads the
  current config through `Connection::getConfig()`. Purging and reconnecting after a switch remain the tenancy
  package's job.
- **Memo.** Each process remembers verified marker keys, so switching back to a tenant already checked in an
  Octane or queue worker costs one array lookup.
- **Locks** are per set and database, so different tenants migrate in parallel.

Integration with a tenancy package is a listener on whatever event it dispatches after switching the connection:

```tyhp
<?tyhp
namespace App\Listeners;

use App\Tenancy\TenantActivated;   // your tenancy package's "tenant switched" event
use Tyhp\Rhetoric\Migrations\Auto\AutoMigrator;

final class MigrateActivatedTenant {
    public function handle(TenantActivated $event): void {
        AutoMigrator::ensure('tenant', set: 'tenant');
    }
}
```

`ensure()` result:

```tyhp
<?tyhp
namespace Tyhp\Rhetoric\Migrations\Auto;

enum MigrationStatus {
    case UpToDate;            // nothing to apply; deferred migrations may still be pending
    case Migrated;            // this call applied migrations
    case BlockedByDeferred;   // a pending deferred migration holds back later migrations
    case Failed;              // inside a failure backoff window with on_failure = 'continue'
}

final class MigrationResult {
    public function __construct(
        public readonly MigrationStatus $status,
        public readonly array<string> $applied,
        public readonly array<string> $deferredPending,
        public readonly bool $fromMarker,   // answered by the hot path, with no database query
    ) {}
}
```

## Laravel integration details

- **Service provider** (auto-discovered through `extra.laravel.providers`) registers configured contexts as
  `scoped` bindings, registers commands, publishes `config/rhetoric.php` and stubs, and loads the mapping cache.
- **Connections:** a context resolves `DatabaseManager::connection($name)`. Read/write connections, sticky reads,
  and `DB::listen` work as they do for Eloquent.
- **Transactions:** `$db->transaction(...)` delegates to `Connection::transaction()`. Rhetoric and Eloquent writes
  can share one transaction.
- **Conventions match Eloquent** (table, column, FK, pivot, timestamp, soft-delete names) so both can map the same
  tables. Conventions are configurable per context.
- **Pagination:** `paginate()` returns `LengthAwarePaginator<int, T>` and `cursorPaginate()` returns `CursorPaginator`.
- **Collections:** `all()` returns `array<T>`; `get()` returns `Illuminate\Support\Collection<int, T>`.
- **Testing:** generated migrations are normal migrations, so `RefreshDatabase` / `LazilyRefreshDatabase` work.
  `$db->createSchema()` is available for fast SQLite in-memory tests.
- **Octane / queue workers:** scoped contexts are reset per request. Long-running jobs should use
  `ContextFactory<T>` or `$db->tracker->clear()`.
- **Auto-migrator (opt-in):** booting hook, Octane and queue `WorkerStarting` listeners, `optimize` integration, and
  `AutoMigrator::ensure()` for tenant switches. See [Auto-migrator](#auto-migrator).
- **Later:** route model binding for Rhetoric models, typed factories for tests, and polymorphic (`morphTo`) relations
  for tables shared with Eloquent. The Eloquent typed-query bridge is required (Phase 12).

rhetoric model that is a Tyhp generic is created with `\Tyhp\Lazy::ghost`, or with `lazy new` after Slice C
has landed. Both bind the type arguments before the constructor.

Ghosts initialize in place and keep identity. Proxies do not (`$proxy !== $real`). References are ghosts so
`Tracker` identity (`spl_object_id`, `$byKey`) stays stable when the object initializes.

On PHP older than 8.4 the helper is eager: same end state, and the object is not lazy. `tyhp/rhetoric`
publishes 803, 804, and 805 (`packages/build-common.sh`, `set_package_dist_builds`). Gate this feature with
`#[\Tyhp\Php]` / `declare(php=…)`, the same way the helper is gated. `output.phpVersion` is a floor and the
803 artifact requires `php: >=8.3`:

- The 804 and 805 builds (floors 8.4 and 8.5) emit the lazy body with no `\PHP_VERSION_ID` check.
- The 803 build emits a `\PHP_VERSION_ID` branch. On PHP 8.3 the eager path runs (`with(fn)`, `$db->load`,
  `$db->loadMissing`). On PHP 8.4+ that same 803 binary takes the lazy path. That branch stays. The compiler
  has no ceiling.

`lazy new` is a compile-time choice of the package floor (`IsPhpVersionAtLeast(8, 4)`), with no runtime
branch. A `lazy new` compiled into the 803 artifact stays eager even when that artifact later runs on PHP
8.4. Prefer `\Tyhp\Lazy::ghost` so the 803 artifact still becomes lazy on PHP 8.4.

`preset` writes a property without initializing
(`ReflectionProperty::setRawValueWithoutLazyInitialization` on 8.4+). `reset` is `resetAsLazyGhost`. Pass
`ReflectionClass::SKIP_DESTRUCTOR` when expiring a live instance so PHP does not run the destructor before
the object becomes lazy again. `json_encode` and normal `serialize` initialize.
`SKIP_INITIALIZATION_ON_SERIALIZE` opts out of serialize only. If the initializer throws, PHP leaves the
object lazy.

`ReflectionProperty::getValue` initializes. `Tyhp\Rhetoric\Tracking\PropertyBag::read` calls `getValue`
after `isInitialized` (`packages/tyhp/rhetoric/tyhp_src/Tracking/PropertyBag.tyhp`). A key that must stay
lazy is read with `ReflectionProperty::getRawValue` (already on the overlay, `getRawValue(T $object): mixed`,
`>=8.4`).

## Risks

- **Expression-tree coverage.** Nested lambdas, arrays and `?->` calls are supported in trees. Constructs the
  compiler still rejects are fixed in Tyhp rather than worked around with string-based escape hatches.
- **Erased generics.** Property and tree types come from compiler stamps, so models compiled by an older Tyhp or
  written in plain PHP fall back to native reflection and need relation attributes or fluent mapping. Mapping
  build reports a relation whose element type it cannot determine.
- **Tyhpdef gaps** in `illuminate-*` will appear as compile errors in the package. Policy: fix the tyhpdef.
- **Laravel version churn.** Pin to the Laravel major the tyhpdefs track (13.x) and add majors deliberately.
- **Name collisions with Laravel vocabulary.** Reusing Laravel method names (`with`, `update`, `delete`, `sole`)
  helps adoption, but behavior must match Laravel's meaning wherever the name matches. Differences (for example,
  `all()` returning `array<T>` rather than a Collection) are called out in the docs.
- **Scope.** EF Core is large. Phases 0–8 are the product (typed queries, unit of work, code-first, the
  auto-migrator, db-first). Later phases are independently shippable. Phases 12 and 13 are required.
- **Auto-migrate: long migrations block requests.** While one process holds the lock, waiting requests occupy
  PHP-FPM workers and database connections, and the pool can run dry. Mitigations: a short HTTP wait (10 s by
  default) followed by a fast 503 with `Retry-After`; deferred migrations for long changes; `rhetoric:migration`
  suggesting `--defer` for data-loss operations; health-check paths in `except_paths`.
- **Auto-migrate: partial failures on MySQL.** MySQL DDL is not transactional, and Laravel records a migration only
  after its `up()` finishes. A migration that fails halfway therefore leaves its earlier statements applied, and the
  next attempt can fail on them. Mitigations: the failure record and backoff stop every request from retrying;
  `on_failure` decides between 503 and continuing; recovery is a manual fix plus `rhetoric:auto-migrate --reset`.
  PostgreSQL, SQL Server, and SQLite run each migration in a transaction (`$withinTransaction`).
- **Auto-migrate: code/schema skew on multi-server deploys.** The first server on a new release migrates while
  servers on the old release still serve requests against the new schema. Mitigations: the expand/contract
  guidance, deferred migrations for the contract step, and the `--defer` suggestion. Old-release servers keep
  their own manifest and marker, so they do not block or re-run anything.
- **Performance.** Tree translation per call could cost more than Eloquent's string builders. The shape-keyed
  translation cache and mapping cache are mandatory, not optional.

### What Phase 1 has to take from this

- Do not call `tyhp/core` string extensions inside a parsable lambda until FOUND_BUGS #12 is fixed. Ordinary method calls already become `methodCall` nodes whose `type` is `mixed`.
- Nullable navigations are `?->` (`nullSafeAccess`). A plain `->` on `?Blog` does not compile.
- Rebind a captured context from the `ConstantExpression` that holds the object, then read its properties. Do not expect a folded scalar.
- Arithmetic in a tree is typed `mixed`. Struct properties stay `propertyAccess` with a `struct` spelling; PHP reflection sees `array` plus `Tyhp\PropertyType`.
- `Connection::transaction` needs an explicit `TReturn` (or a closure return the checker can infer). Do not call `orderBy`, or any other signature that spells `Eloquent\Builder<mixed>`, until FOUND_BUGS #13 is fixed.
- Drive `Migrator` directly. Match install-repository, then schema load, then `runPending`. Do not add `MigrateCommand` to the tyhpdef for that. `--isolated` is a cache mutex and is separate from the advisory lock.
- PostgreSQL: session advisory locks survive a temp DDL statement, `lock_timeout` cancels the waiter, and the lock dies with the session. SQLite: `flock` a sidecar file. MySQL, MariaDB, SQL Server, and PgBouncer are still unmeasured. - Throw `ServiceUnavailableHttpException` from the booting callback for the 503. The request path is already available there, so `except_paths` can skip before routing. In console, read the command from `argv` during boot; the artisan application has not resolved it yet.
- Octane's worker boot already runs booting callbacks before `WorkerStarting`. Memoize so the two hooks do not migrate twice. The order is unverified until Octane is installed.
- `optimizes()` only adds names to the optimize task lists. The artisan commands still have to be registered.
- On the 8.3 polyfill, hooked properties are invisible to `ReflectionProperty`. The polyfill keeps each property's `backed` flag in a private array inside the protected `__tyhpPropertyHook` (`PropertyAccessorObject`), with no public reader, so Phase 2 needs either a public accessor on `PropertyAccessorObject` or the compiler to record the flag another way. `ReflectionProperty::isVirtual()` exists only on PHP 8.4+; there it is false for a backed hook.
- Marker visibility across FPM workers with `opcache.validate_timestamps=0` is still untested.
